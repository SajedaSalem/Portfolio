Getestete Application

Eine kleine Flask-API mit CI-freundlichen Runtime Checks.

Die Server Inventory API verwaltet ein JSON-basiertes Inventar mit neun Beispielservern aus Production, Staging und Development. Die Inventory-Logik ist von der HTTP-Schicht getrennt, sodass sowohl die Application-Logik als auch das API-Verhalten unabhängig getestet werden können. Health-, Readiness- und Version-Endpoints geben der Smoke Stage anschließend konkrete Runtime-Bedingungen für die Verifikation.

EndpointZweck
GET /healthzBestätigt, dass die Application läuft
GET /readyzBestätigt, dass das Inventar geladen ist
GET /versionGibt die konfigurierte CI-Build-Version zurück
GET /serversGibt verfügbare Server zurück
GET /servers/<name>Gibt einen bestimmten Server zurück
GET /statsGibt Inventarstatistiken zurück
Workflow-Trigger

Automatische Quality Gates mit manueller Kontrolle.

Ein Push auf main validiert Code, der den Branch erreicht. Pull Requests mit Ziel main werden vor dem Merge geprüft, und workflow_dispatch stellt dieselbe Validierung bei Bedarf direkt über die GitHub-Actions-Oberfläche bereit.

  push:

  pull_request:

Runner & Python-Umgebung

Reproduzierbares Setup bei jedem Lauf.

Jeder Lauf startet auf einem von GitHub bereitgestellten ubuntu-latest Runner. Das Repository wird ausgecheckt, die benötigte Python-Version installiert und die Projektabhängigkeiten werden aus requirements.txt geladen. Pip-Caching ermöglicht es späteren Läufen, bereits heruntergeladene Abhängigkeiten wiederzuverwenden. Da dieses Setup in CI definiert ist, hängt die Validierung nicht davon ab, welche Pakete zufällig auf dem Entwicklerrechner installiert sind.

ci.yml · Runner & Python setup
.github/workflows/ci.yml
YAML ansehenCI-Lauf ansehen ↗
runs-on: ubuntu-latest
steps:
  - uses: actions/checkout@v4

  - uses: actions/setup-python@v5
    with:
      python-version: ${{ matrix.python-version }}
      cache: "pip"

  - run: pip install -r requirements.txt
Codequalität & automatisierte Tests

Früh bei Qualitätsproblemen stoppen, danach Verhalten verifizieren.

Die Reihenfolge der Validierung ist bewusst gewählt. Bevor die Testsuite startet, führt flake8 statische Code-Quality-Checks anhand der Linting-Konfiguration des Projekts aus. Verstößt der Quellcode gegen diese Regeln, stoppt die Pipeline bereits am Quality Gate, statt mit Application-Tests für Code fortzufahren, der die erste Validierung nicht bestanden hat.

Nach erfolgreichem Linting führt pytest die automatisierten Tests aus. Die Option -q hält die CI-Ausgabe kompakt, während --junitxml=report.xml einen strukturierten JUnit-Report erzeugt, der über die Lebensdauer des temporären Runners hinaus gespeichert werden kann. Damit prüft die Stage sowohl Codequalität als auch Application-Verhalten und erzeugt gleichzeitig diagnostische Informationen für eine spätere Auswertung.

Tests mit mehreren Versionen

Eine Job-Definition, zwei Python-Versionen.

Anstatt den gesamten Test-Job zu duplizieren, erzeugt eine Matrix-Strategie aus einer einzigen Definition unabhängige Läufe für Python 3.11 und 3.12. fail-fast: false ist für die Diagnose hilfreich, weil ein Fehler in einer Version den anderen Matrix-Lauf nicht abbricht; beide Kompatibilitätsergebnisse bleiben sichtbar.

ci.yml · Python matrix
.github/workflows/ci.yml
YAML ansehenCI-Lauf ansehen ↗
strategy:
  fail-fast: false
  matrix:
    python-version:
      - "3.11"
      - "3.12"

python-version: ${{ matrix.python-version }}

Testberichte & Artefakte

Nachweise erhalten, auch nachdem der Runner beendet ist.

Jeder Testlauf erzeugt report.xml. Der Report wird als GitHub-Actions-Artefakt hochgeladen, sodass das strukturierte Testergebnis auch nach Ende des temporären Runners verfügbar bleibt. Der Upload verwendet bewusst if: always(): Gerade bei einem fehlgeschlagenen Testlauf sind diagnostische Informationen besonders wertvoll, daher soll das Artefakt nicht verschwinden, nur weil pytest einen Fehler zurückgegeben hat.

ci.yml · Test artifact
.github/workflows/ci.yml
YAML ansehenCI-Lauf ansehen ↗
- name: Upload test report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: test-report
    path: report.xml
Runtime Smoke Tests

Bestehende Tests bedeuten nicht automatisch, dass die Application erfolgreich startet.

Der zweite Job, smoke, startet erst, nachdem der Test-Job erfolgreich war. Er läuft auf einem weiteren frischen Runner und kann sich deshalb nicht auf die in der Test Stage vorbereitete Umgebung verlassen. Der Job wiederholt das notwendige Setup, startet die Flask API im Hintergrund und kommuniziert anschließend per HTTP mit der laufenden Application. Damit wird nicht nur geprüft, ob Funktionen in Tests korrekt arbeiten, sondern auch, ob der Service in einer sauberen Runtime-Umgebung tatsächlich startet und antwortet.

ci.yml · Start API & health check
.github/workflows/ci.yml
YAML ansehenCI-Lauf ansehen ↗
smoke:
  needs: test
  runs-on: ubuntu-latest

- name: Start the API
  run: |
    python app.py &
    sleep 5

- name: Check health endpoint
  run: |
    code=$(curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5000/healthz)
    echo "got $code"
    test "$code" = "200"

GET /healthz

Prüft, ob die Application erreichbar ist, und erwartet ausdrücklich HTTP 200.

GET /readyz

Prüft zusätzlich, ob das erwartete Inventar mit neun Servern geladen wurde.

Runtime-Unterscheidung

Running ≠ Ready

Die beiden Endpoints unterscheiden damit zwischen einem laufenden Prozess und einer Application, die mit ihren Daten tatsächlich bereit ist.

CI-Build-Identifikation

Die laufende Application mit ihrem CI-Lauf verknüpfen.

Während der Smoke Stage wird die GitHub-Run-Nummer über APP_VERSION an die Application übergeben. Der /version Endpoint wird anschließend auf denselben Wert geprüft. Dadurch entsteht eine einfache Verbindung zwischen einem GitHub-Actions-Lauf und der zugehörigen Application-Instanz, ohne eine neue Version direkt im Quellcode zu hardcoden.

ci.yml · Build-Identifikation
.github/workflows/ci.yml
YAML ansehenCI-Lauf ansehen ↗
env:
  APP_VERSION: ci-${{ github.run_number }}

# Runtime check:
GET /version  →  ci-${{ github.run_number }}
Kontrollierter Fehlertest

Sicherstellen, dass CI eine fehlerhafte Änderung ablehnen kann.

Eine CI-Pipeline sollte Fehlererkennung genauso deutlich demonstrieren wie erfolgreiche Läufe. Auf einem separaten break-it Branch wurde eine Test-Erwartung absichtlich geändert, sodass die Suite fehlschlug. Anschließend wurde für diesen Branch ein Pull Request gegen main geöffnet. GitHub Actions erkannte die Regression, zeigte einen fehlgeschlagenen Check im Pull-Request-Interface und die Änderung wurde geschlossen, ohne gemergt zu werden.

Technische Entscheidungen

Warum die Pipeline so aufgebaut ist.

Der Workflow trennt Verantwortlichkeiten, sodass Codequalität, Kompatibilität, diagnostische Reports und Runtime-Verhalten jeweils gezielt geprüft werden, statt alles in einem undurchsichtigen „Build“-Schritt zusammenzufassen.

Getrennte Test- und Smoke-Jobs

Tests validieren Logik und API-Verhalten. Ein zweiter frischer Runner belegt zusätzlich, dass die Application tatsächlich starten und echte HTTP-Anfragen beantworten kann.

Matrix statt duplizierter Jobs

Eine wartbare Workflow-Definition erzeugt unabhängige Kompatibilitätsergebnisse für Python 3.11 und 3.12.

Artefakte bleiben auch bei Fehlern erhalten

Die JUnit-Ausgabe bleibt auch bei fehlgeschlagenen Tests erhalten und liefert damit weiterhin nützliche Informationen für das Troubleshooting.

Runtime-Metadaten über Environment-Konfiguration

Die CI-Run-Nummer erreicht die Application über Konfiguration statt über Änderungen am Quellcode.

Was ich gelernt habe

CI ist ein Validierungssystem und nicht nur ein grüner Haken.

Das Projekt verband Repository-Events, saubere Runner, Linting, automatisierte Tests, Matrix-Kompatibilität, Artefakt-Management, Job-Abhängigkeiten, environment-basierte Konfiguration und HTTP Smoke Testing zu einem reproduzierbaren Prozess. Besonders wertvoll war der kontrollierte Fehlertest, weil er zeigte, dass die Pipeline eine ungültige Änderung tatsächlich erkennen und sichtbar machen kann — statt nur erfolgreiche Builds zu demonstrieren.

Ausblick: Security Scanning → Container Image Build → automatisiertes Deployment. Diese Punkte sind als zukünftige Erweiterungen gedacht und werden nicht als bereits umgesetzt dargestellt.
