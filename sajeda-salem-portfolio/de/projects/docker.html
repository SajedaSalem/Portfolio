01 · Statische Web-Auslieferung

Eine Portfolio-Website in einem eigenständigen Nginx-Container ausführen

Das Projekt beginnt mit einem einfachen, eigenständigen statischen Web-Deployment. Eine einzelne Portfolio-Datei index.html wird über einen Nginx-Container ausgeliefert.

Dieser Schritt ist bewusst einfach gehalten: Zuerst soll der grundlegende Container-Workflow verstanden werden, bevor Shared Content, mehrere Container-Instanzen oder Compose hinzukommen. Die Website-Datei wird Nginx bereitgestellt, der Container gestartet, ein Host-Port veröffentlicht und die Seite anschließend im Browser verifiziert.

Zu diesem Zeitpunkt gibt es nur eine Website-Datei und einen Web-Container. Shared Content zwischen mehreren Containern kommt erst im nächsten Schritt hinzu.

Praktische Umsetzung
  • Prepared a standalone portfolio index.html.
  • Nginx als einzelnen containerisierten Webserver ausgeführt.
  • Container über einen Host-Port veröffentlicht.
  • Portfolio im Browser geöffnet und die Auslieferung verifiziert.

02 · Shared Content & mehrere Web-Instanzen

Eine gemeinsame Website über mehrere Nginx-Container ausliefern

Nach dem eigenständigen Deployment wird die Umgebung auf mehrere Webserver-Instanzen erweitert. Zwei unabhängige Nginx-Container liefern dieselbe Website-Quelle aus ./site.

Dasselbe Host-Verzeichnis wird in beide Container gemountet. Dadurch teilen sie sich eine Content-Quelle, während ihre Container-Lebenszyklen unabhängig bleiben.

volumes:
  - ./site:/usr/share/nginx/html:ro

Der :ro Mount hält die Website aus Sicht der Container read-only. Nginx kann die Dateien lesen und ausliefern, aber den Inhalt auf dem Host nicht verändern.

Die Umsetzung wurde in zwei Schritten verifiziert: Beide Container wurden unabhängig mit curl abgefragt. Anschließend wurde die gemeinsame Website-Datei bearbeitet, um zu bestätigen, dass die aktualisierten Inhalte über beide Endpoints sichtbar wurden, ohne die Container neu zu bauen.

Praktische Verifikation
  • Zwei unabhängige Nginx-Container gestartet.
  • Dasselbe ./site Verzeichnis in beide Container gemountet.
  • Beide Container unabhängig mit curl verifiziert.
  • Gemeinsame Website-Datei bearbeitet.
  • Beide Endpoints neu abgefragt und dieselben aktualisierten Inhalte bestätigt.

04 · Application-Konfiguration

Runtime-Konfiguration außerhalb der Application-Logik halten

Die API liest HOST, PORT und APP_ENV aus der Runtime-Umgebung. Defaults halten die lokale Ausführung einfach, während Environment Variables denselben Code in anderen Deployments unterschiedlich konfigurieren können.

Beispielsweise gibt GET /health den aktuellen Application-Status zusammen mit der aktiven Umgebung zurück. Dadurch wird die Konfiguration sichtbar, ohne umgebungsspezifische Werte fest in die Application zu schreiben.

Runtime-Werte
HOST=0.0.0.0 PORT=8000 APP_ENV=local

05 · Datenmodell

Persistenz bewusst einfach halten

Die aktuelle API speichert Server-Einträge in einem In-Memory-Python-Dictionary. Jeder Eintrag enthält id, name, ip und env.

Das ist bewusst einfach gehalten, damit der Fokus auf API-Verhalten, Containerisierung und Service-Architektur bleibt. Da die Daten im Speicher liegen, bleiben sie nach einem Neustart des Prozesses oder einer Neuerstellung des Containers nicht erhalten.

Umsetzungsgrenze: Redis existiert später in der Compose-Umgebung als interner Infrastruktur-Service, wird aber nicht als integrierter Application-Speicher dargestellt. Die API nutzt weiterhin ihre In-Memory-Datenschicht.
Praktische Verifikation
  • Server-Einträge über die API erstellt und abgefragt.
  • Mit dem leichtgewichtigen In-Memory-Server-Inventar gearbeitet.
  • Redis klar von der aktuellen Application-Datenschicht getrennt gehalten.

06 · FastAPI-Containerisierung

Die FastAPI-Runtime unabhängig vom Host als Container bereitstellen

Nachdem Application-Verhalten und Datenmodell feststehen, wird der FastAPI-Service in ein eigenes Container Image überführt. Das Dockerfile verwendet python:3.12-slim, erstellt /app als Working Directory, installiert Abhängigkeiten aus requirements.txt, kopiert die Application und exponiert Port 8000.

FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .

EXPOSE 8000
CMD ["python", "app.py"]

Damit werden Python-Runtime und Abhängigkeiten Bestandteil des Container Images und müssen nicht auf dem Host vorinstalliert sein.

Praktische Verifikation

  • Image gebaut.
  • Containerisierte Application ausgeführt.
  • Container-Logs verifiziert.

07 · Docker-Compose-Orchestrierung

Den gesamten Stack als eine Umgebung verwalten

Docker Compose definiert die Multi-Container-Umgebung deklarativ in einer Compose-Datei. Statt Container-Einstellungen manuell nachzubauen, hält die Datei Services, Build-/Image-Konfiguration, Ports, Volumes und Runtime-Beziehungen des Stacks fest.

Die vollständige Umgebung wurde im Detached Mode gestartet und aus mehreren Perspektiven verifiziert. docker compose ps bestätigte den Service-Status, HTTP-Anfragen verifizierten die veröffentlichten Services und Redis wurde über eine erfolgreiche PONG Response geprüft. Abschließend wurde die Umgebung als eine Einheit gestoppt und entfernt.

  • Die funktionierende Compose-Umgebung über Service-Status, HTTP-Checks und Redis PONG verifiziert.
  • Stack als eine Einheit gestoppt und entfernt.

08 · Docker Networking & DNS

Konnektivität und Namensauflösung testen auf mynet

Diese Networking-Übung ist vom Compose-Stack getrennt. Ein benutzerdefiniertes Bridge Network mit dem Namen mynet wurde erstellt und zwei eigenständige Container — nodeA und nodeB — wurden damit verbunden.

Da beide Container dasselbe benutzerdefinierte Netzwerk verwenden, können sie direkt miteinander kommunizieren. Dockers eingebettetes DNS ermöglicht außerdem die Namensauflösung über Container-Namen, statt sich auf fest eingetragene IP-Adressen zu verlassen.

Das Netzwerk wurde inspiziert, um die Mitgliedschaft zu bestätigen, und die Namensauflösung wurde direkt zwischen beiden Nodes getestet.

Praktische Verifikation
  • mynet erstellt.
  • nodeA und nodeB im selben Netzwerk gestartet.
  • mynet inspiziert und bestätigt, dass beide Container verbunden waren.
  • Docker-DNS-Namensauflösung zwischen den Nodes verifiziert.

09 · Netzwerkisolation

Nachweisen, dass DNS und Konnektivität an Netzwerkgrenzen enden

Ein zweites benutzerdefiniertes Netzwerk, isolated-net, platziert einen weiteren Container außerhalb von mynet. Damit wird das Gegenteil des vorherigen Tests geprüft: Container ohne gemeinsames Docker-Netzwerk sollen nicht automatisch kommunizieren oder sich über Docker DNS auflösen können.

Der fehlgeschlagene Cross-Network-Kommunikations- und Namensauflösungsversuch dient daher als Nachweis der Isolation. Docker Networking stellt nicht nur Konnektivität bereit, sondern auch klare Kommunikationsgrenzen.

Praktische Verifikation
  • Separates isoliertes Docker-Netzwerk erstellt.
  • Test-Container außerhalb von mynet platziert.
  • Cross-Network-Kommunikation und DNS-Auflösung versucht.
  • Bestätigt, dass DNS/Konnektivität über die isolierte Netzwerkgrenze hinweg nicht funktionierte.

10 · Verifikation & Troubleshooting

Application-Verhalten, Service-Status und Runtime-Ausgabe prüfen

Das Projekt wurde auf mehreren Ebenen verifiziert, statt einen laufenden Container bereits als Beweis für eine funktionierende Gesamtumgebung zu betrachten. Ein HTTP-Health-Request prüfte das Application-Verhalten, docker compose ps zeigte den Status der Compose-Services und Container-Logs machten das Runtime-Verhalten des FastAPI-Services sichtbar.

These checks answer three useful troubleshooting questions: Antwortet die Application?, Laufen die erwarteten Container?, and Was meldet die Application beim Start und während der Ausführung?
