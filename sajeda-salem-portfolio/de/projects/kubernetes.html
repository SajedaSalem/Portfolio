Kubernetes Microservices & GitLab CI/CD Platform

Ein End-to-End-DevOps-Projekt, das eine Zertifizierungsplattform mit zwei Services von der lokalen Entwicklung über Docker Images und Kubernetes-Orchestrierung bis zu Private Registry Access, automatisierten Tests und Trivy Security Scanning mit GitLab CI/CD führt.

GitHub Repository ansehen ↗GitLab Projekt ansehen ↗Kontakt
Projektziel

Den gesamten Delivery Path verbinden.

GloryTech Academy ist eine Trainingsplattform mit zwei Services: einem Nginx-Frontend und einer Node.js/Express-Backend-REST-API. Ziel war nicht nur, beide Services zum Laufen zu bringen, sondern Code, Container, Registry Access, Kubernetes Networking, CI/CD und Security Validation zu einem funktionierenden Gesamtsystem zu verbinden.

Für das Lab verwendete Architektur: zwei unabhängig deploybare Services innerhalb des glorytech-academy Namespace, verbunden über Kubernetes Services und einen Nginx Reverse Proxy.

01 · Application & API

Die Application vor der Orchestrierung aufbauen und verifizieren.

Das Backend stellt Kursdaten über eine REST API bereit und enthält Health Checks für die spätere Container- und Kubernetes-Verifikation. Die Filterlogik unterstützt Vendor-, Category-, Level- und Search-Parameter; automatisierte Tests prüfen erfolgreiche Responses, Filterverhalten und 404-Handling.

Durch das frühe Testen der Application konnten spätere Docker- und Kubernetes-Probleme klar von Application-Fehlern getrennt werden.

Backend

03 · Kubernetes Deployment

Zwei Container in einen resilienten Cluster-Workload überführen.

Das Kubernetes-Manifest erstellt einen eigenen Namespace und bildet die Zwei-Service-Architektur mit separaten Deployments und Services ab. 04 · Konfigurationsmanagement

ConfigMaps auf zwei unterschiedliche Arten einsetzen.

Das Projekt verwendet bewusst zwei ConfigMaps, um Runtime-Konfiguration von Container Images zu trennen. Die Backend-Konfiguration wird als Environment Variables injiziert, während die Nginx-Konfiguration des Frontends als Datei gemountet wird. Dadurch bleiben umgebungsspezifische Einstellungen außerhalb des Images und zwei typische Kubernetes-Konfigurationsmuster werden praktisch umgesetzt.

backend-config

Vom Backend Deployment als Environment-Konfiguration referenziert, statt Runtime-Werte fest in das Image zu schreiben.

frontend-nginx-conf

In die Frontend Pods gemountet, damit Nginx API-Traffic an den Backend Service innerhalb des Clusters weiterleiten kann.

05 · Service-Kommunikation

Den Browser einfach halten; Nginx übernimmt die Kommunikation mit Kubernetes.

Der Browser kann einen internen Kubernetes-Service-DNS-Namen nicht direkt auflösen. Das Frontend verwendet daher einen Same-Origin-Pfad wie /api/courses. Nginx läuft innerhalb des Clusters und leitet diese Anfrage per Reverse Proxy an den Backend Service weiter. Dadurch bleibt die interne Service Discovery in Kubernetes und das Backend muss nicht direkt zum Browser exponiert werden.

06 · Private Registry Access

Kubernetes Zugriff geben, ohne Credentials zu committen.

Die CI-Pipeline veröffentlicht private Service Images in der GitLab Container Registry. Kubernetes benötigt eigene Credentials zum Pullen dieser Images. Deshalb wird ein Registry Secret direkt im Cluster erstellt und von den Deployments über imagePullSecrets referenziert. Das Deploy Token wird nicht in Git committed.

Registry authentication pattern
cluster-side secret · not stored in Git
kubectl create secret docker-registry gitlab-registry-secret \
  --docker-server=registry.gitlab.com \
  --docker-username=<deploy-token-user> \
  --docker-password=<deploy-token> \
  --namespace=glorytech-academy

Deployment → imagePullSecrets → gitlab-registry-secret
Security-Entscheidung: Registry Credentials bleiben im Cluster, statt im Manifest eingebettet oder ins Repository committed zu werden.
07 · GitLab CI/CD

Bei jedem Delivery Cycle bauen, testen und scannen.

Die GitLab-Pipeline verbindet Source Control, Container Registry und Quality Gates. Die Build Stage erstellt und veröffentlicht Frontend- und Backend-Images, die Test Stage führt die Backend-Automation aus und die Security Stage scannt das erzeugte Backend-Image mit Trivy, bevor der Delivery Path als erfolgreich gilt.

Der Delivery Path des Projekts führt von Code und Version Control über Image Build, Tests und Security Scanning bis zum Kubernetes Deployment.

08 · Security Gate & Troubleshooting

Das Ziel war nicht, den Fehler zu umgehen, sondern seine Ursache zu beheben und die Pipeline anschließend erfolgreich durchlaufen zu lassen.

Trivy blockierte die Pipeline zunächst aufgrund kritischer Vulnerabilities im Backend Base Image. Statt die Security Stage zu umgehen, wurde die Ursache auf die Image-Wahl zurückgeführt. Das Backend Image wurde angepasst, neu gebaut und erneut gescannt, bis das Security Gate erfolgreich war.

Zentrale Erkenntnis: Troubleshooting wurde zu einer End-to-End-Aufgabe. Ein Fehler auf einer Ebene konnte seinen Ursprung im Code, Image, Registry Access, in der Kubernetes-Konfiguration, im Networking oder in CI/CD haben.
09 · Abschließende Verifikation

Das System verifizieren, nicht nur das YAML.

Die abschließende Verifikation prüft sowohl den gewünschten Kubernetes-Zustand als auch das tatsächliche Application-Verhalten: Pods laufen, Deployments sind 2/2 verfügbar, Services sind vorhanden und der extern erreichbare Frontend-Pfad liefert echte Backend-Health- und Kursdaten.

Was ich gelernt habe

Die Tools sind getrennt. Das System ist es nicht.

Der wertvollste Teil dieses Projekts war das Verbinden der einzelnen Ebenen und das Troubleshooting an ihren Schnittstellen. Einen Container zu bauen ist etwas anderes, als ihn aus einer Private Registry zu pullen; Running Pods bedeuten nicht automatisch funktionierende Service-Kommunikation; und eine CI-Pipeline ist besonders dann nützlich, wenn sie ein unsicheres Image stoppen kann, statt nur Erfolg zu melden.
